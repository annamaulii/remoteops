# RemoteOps

Backend-first platform for managing distributed teams and contractors.

## Run with Docker

Create a private environment file and replace its placeholder secrets:

```bash
install -m 600 .env.example .env
openssl rand -hex 32
docker compose up --build
```

Use the generated value for both PostgreSQL password placeholders in `.env`,
then generate separate values for the JWT and webhook signing secrets.

The API is available at <http://127.0.0.1:8000/docs>. PostgreSQL stays on
`127.0.0.1:5432`; migrations run before the API and webhook worker start.

```bash
docker compose logs -f api webhook-worker
docker compose down
```

`docker compose down` preserves PostgreSQL data. Use `docker compose down -v`
only when you intentionally want to delete the database volume and its data.

## Rollback

The `migrate` service runs `alembic upgrade head` automatically on every
`docker compose up`. To undo the most recent migration:

```bash
docker compose run --rm migrate alembic downgrade -1
```

Then restart the API so it picks up the reverted schema:

```bash
docker compose restart api
```

Rolling back a migration does not restore data dropped by that migration's
`upgrade()` step; it only reverses the schema change. Restore the `postgres_data`
volume from a backup if you need the data back too.

## Local development

```bash
python -m pip install -e ".[dev]"
docker compose up -d postgres
alembic upgrade head
pytest
ruff check remoteops tests migrations/env.py
ruff format --check remoteops tests migrations/env.py
mypy remoteops
```

## Frontend

The `frontend/` directory is a Vite + Vue 3 + TypeScript app covering the
core workflow: log in, pick or create an organization, add a project and a
contractor, log work, and approve or reject it.

```bash
cd frontend
cp .env.example .env   # VITE_API_BASE_URL, defaults to http://localhost:8000
npm install
npm run dev             # http://localhost:5173
npm run test
npm run typecheck
npm run build
```

The API must have `CORS_ALLOWED_ORIGINS=http://localhost:5173` set (see the
backend `.env.example`) or the browser will block every request.

## Deployment

**Live URLs:** not yet deployed — see below.

`render.yaml` at the repository root is a ready-to-use
[Render Blueprint](https://render.com/docs/blueprint-spec) that deploys the
API (from the existing `Dockerfile`), a managed PostgreSQL database, and the
frontend as a static site, all under one account. Render was chosen because
it's the simplest single-provider fit for this repo's existing
Docker-based backend plus a static frontend build — no new infrastructure
or architecture, just deployment config for what already exists.

To deploy:

1. Create a free account at <https://render.com> and connect this GitHub repo.
2. **New +** → **Blueprint** → select this repo. Render reads `render.yaml`
   and proposes `remoteops-db`, `remoteops-api`, and `remoteops-frontend`.
3. Before applying, open `remoteops-db` once created and copy its **Internal
   Connection String**. On `remoteops-api`, set `DATABASE_URL` to that string
   with the scheme changed from `postgresql://` to `postgresql+psycopg://`
   (this app uses psycopg3, and Render's connection string doesn't include
   the driver suffix — the blueprint deliberately leaves this field manual
   rather than risk a silently wrong auto-wired value).
4. `JWT_SECRET` and `WEBHOOK_SIGNING_SECRET` are auto-generated by Render.
5. Apply the blueprint and wait for both web services to deploy.
   `preDeployCommand: alembic upgrade head` runs migrations automatically.
6. If either service lands on a URL different from
   `remoteops-api.onrender.com` / `remoteops-frontend.onrender.com` (e.g. the
   name was taken), update `CORS_ALLOWED_ORIGINS` on `remoteops-api` and
   `VITE_API_BASE_URL` on `remoteops-frontend` to match, then redeploy both.
7. Verify `GET https://<api-url>/health` and `/ready` both return 200, then
   walk through login → organization → project → work log → approval in the
   browser at the frontend URL.

### Known limitations

- No project/contractor/organization editing or deletion in the UI — only
  create and list, matching the roadmap's "minimal" scope for this stage.
- The access token lives in memory only and the refresh token in
  `sessionStorage` (not `localStorage`); both are lost if the tab is closed.
  This is a deliberate trade-off, not an oversight — the backend issues
  bearer tokens rather than httpOnly cookies, so this is the safer option
  available without a backend auth redesign. See the comment in
  `frontend/src/stores/auth.ts`.
- No pagination controls in the UI yet — list views show the first page
  only (the backend's pagination/filtering from Week 8 isn't surfaced here).
- The webhook delivery worker (`remoteops/worker.py`) is not part of the
  Render blueprint — it isn't needed for the login → organization → project
  → work log → approval workflow, and deploying it costs an extra service
  for a feature this deployment doesn't exercise. Add a `worker` service
  running `python -m remoteops.worker` with the same env vars if needed.
- Render's free tier spins down idle web services and expires free
  databases after 30 days — fine for a portfolio demo, not for real use.
- Visual design is intentionally minimal — one shared stylesheet, no
  component library, one responsive breakpoint.
